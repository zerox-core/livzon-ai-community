## P0 前置 Bug 修复（地基）

### P0-1 报名表原始字段名暴露（field_a / field_b / field_c）

**根因（已定位，双因叠加）**：
1. `public/app.js` afCollect（约 L832-856）：管理端保存表单时，label 留空则直接以 key 兜底存入配置——管理员漏填标签时，原始 key 就进了用户侧渲染。
2. 存量数据：`activity_signup_forms.profile.fields` 里已存在 label 为空/等于 key 的脏配置。

**改动点**：
- 管理端 afCollect：label 为空时**保存前拦截**（提示「自定义字段必须填写标签」），不再静默兜底。
- 用户侧 fieldHtml 渲染前：label 为空或与 key 相同且形如 `field_\w+` 时，展示「信息项 N」类兜底文案而非原始 key（防御旧数据）。
- 一次性数据修复：SQL 或管理端入口，扫描 `activity_signup_forms` 全部 profile.fields，列出 label 缺失项，由管理员补录中文标签（**不自动猜标签，只报清单**）。

**涉及文件**：`public/app.js`（afCollect / fieldHtml 调用处）；数据修复脚本走一次性 SQL。

**验收**：任一活动报名页不再出现 `field_*` 形态的字段名；管理端无法保存无标签字段；存量脏配置有清单可修。

### P0-2 部门自动读取为空

**根因（已定位）**：`server/routes/auth.js` upsertUser 将 `department_ids[0]`（原始部门 ID）写入 `users.department`；`/api/my/profile` 原样返回，报名表只读展示的就是 ID 或空串。

**改动点**：
- 登录链路：upsertUser 时用 access_token 调飞书通讯录接口把 department_ids 解析为部门名称（解析失败保留原值，不阻断登录）。
- 存量数据：提供一次性回填脚本（遍历 users，逐个解析部门名），或降级方案——前端展示时若值为纯 ID/空则显示「未设置」。
- `userSnapshot`（`server/lib/community-core.js`）路径同步受益，报名落库的 dept 一并正确。

**涉及文件**：`server/routes/auth.js`；一次性迁移脚本；`server/lib/lark-client.js`（若需新增部门名查询封装）。

**验收**：重新登录后报名表部门显示中文部门名；老用户回填后同样正常。

### P0-3 页面卡顿排查（录屏中两次卡死）

**现象**：录屏全程页面两次明显冻结（「怎么卡住了」「怎么又卡了」）。

**排查方向（按嫌疑排序）**：
1. 主线程长任务：app.js 体积已 6400+ 行，嫌疑点是 canvas 动画（活动大厅视觉区）与大量 innerHTML 拼接渲染同帧执行；录屏软件叠加会放大。
2. 接口阻塞：报名页 `Promise.all` 4 个请求（activity / signup-form / auth/me / my/profile），若某接口慢，按现状无 loading 态，页面看似卡死。
3. 复现手段：Performance 面板录一段常规操作（进报名页→填表→上传），定位长任务；服务端看 server.log 对应时间片。

**产出**：定位结论 + 修复。若为渲染问题，给卡顿区块加 `requestIdleCallback`/分帧；若为接口问题，加骨架屏与超时提示。

**验收**：同路径连续操作 10 次无肉眼可见冻结（录屏佐证）。

### P0-4（待确认，不排期）活动记录凌晨时间

个人中心活动记录显示 `2026-09-07 01:48` 等凌晨时间，疑为 UTC/本地时区或写入时间口径问题。**先取证**（查 activity_records 相关写入点的时间来源）再决定是否修复；不确认前不动。

## P1 报名表改造（布局重做 + 字段规则 + 自动草稿）

**前提**：P0-1、P0-2 完成。

### P1-1 布局重做

**现状问题**：单列平铺、无分组、字段无说明文案，小白看不懂字段含义（需求澄清 §2.1 原话「太简陋」）。

**改动点**（`public/app.js` SignupPage + `public/index.html` 样式）：
- 卡片分组：①基本信息（姓名/部门，只读，带「自动读取自飞书账号」说明文案）→ ②联系方式（含绑定手机号展示）→ ③作品文件（含分流引导，见 P2）→ ④活动自定义信息（fieldHtml 字段组）→ ⑤提交区。
- 每个字段配一行灰字说明（placeholder + hint），必填星号统一规范。
- 顶部加进度提示（如「1/2 步」），降低长表单压迫感。
- 失焦即时校验，错误文案内联到字段下方（现状是提交时统一报「请填写：xxx」）。

### P1-2 字段规则

| 字段 | 实现 |
| --- | --- |
| 姓名 | 只读预填（现状已实现，保持）；为空时显示「请先在飞书完善姓名」并允许手填一次（兜底脏数据用户） |
| 部门 | 只读预填，依赖 P0-2 数据修复；为空显示「未设置」 |
| 备用联系方式 | label 改「备用联系方式（选填）」+ 字段下方展示「账号绑定手机号：139****1234」（从 `/api/my/profile` 的 email/mobile 取，脱敏显示），输入框 placeholder「如需短信之外的通知渠道请填写」 |

**涉及文件**：`public/app.js` SignupPage；如需手机号需确认 users 表/飞书侧是否取得到（**待确认项 ①**：users 表当前无 mobile 字段，需确认取号路径——飞书 users.info 的 mobile 字段或让用户手填）。

### P1-3 自动草稿（不能丢）

**方案**：localStorage 为主，服务端不新建表（首版）。
- key：`signup_draft:{activityId}:{userId}`，value：`{contact, response, updatedAt}`（文件不入草稿，只记「已选/已传资源引用」）。
- 触发：input/change 事件 debounce 500ms 写入。
- 恢复：进入报名页时读取草稿，若与空表单有差异，顶部提示「已恢复上次编辑内容（时间）+ 清空」按钮。
- 清除：提交成功后删除；用户点「清空」删除。
- 边界：登录态变化/活动模板字段变更（key 集合变化）时，草稿按 key 逐字段恢复，不整体覆盖。

**验收**：填一半→关页→重进，内容完整恢复；提交成功后草稿清除；两个活动之间草稿互不干扰。

## P2 上传链路分流（报名表 ↔ 我的资源打通）

**前提**：P1 完成。这是需求澄清 §三的完整落地，也是「作品与资源打通」核心原则的实现。

### P2-1 已有资源直接选用

**改动点**（`public/app.js` SignupPage + 复用 `/api/assets?mine=1`）：
- 报名表「作品文件」区改为两种模式：**选用已有**（默认，若 `mine=1` 列表非空）／**现场新传**。
- 「选用已有」：列出本人资源（名称/分类/大小/时间，单选），选中后随报名提交 `{upload: {assetId, ...}}`。
- 服务端 `POST /:id/signup`：upload 支持 assetId 引用——校验该 asset 属于当前用户，报名记录存 asset 引用（**注意**：现状 upload 存的是 `{filename,size,storage_url}` 快照，需增加 `asset_id` 字段并在删除资产时同步置空引用，与现有 DELETE 资产的级联逻辑对齐——见 `server/routes/assets.js` DELETE 处理）。
- 现场新传走现有 `/:id/signup/upload`（已登记 assets，天然进「我的资源」——这条链路已通，保持）。

### P2-2 按类型分流 + 压缩包注释

**改动点**（前端为主）：
- 文件选择控件上方固定文案：「上传程序类、SKILL 类请先进行压缩，上传压缩包即可」。
- 选中文件后按扩展名/类型判断：`.zip/.rar/.7z/.tar.gz` → 提示「已识别压缩包，将按原格式存入我的资源」；检测到多文件文件夹选择意图或常见源码扩展名（`.py/.js/.kt/...` 散文件）→ 引导压缩；视频/图片/文档 → 走现有普通上传。
- 「不会压缩」兜底：上传区下方常驻入口「不会打包压缩？→ 去我的资源上传」，点击带参数跳个人中心（见 P3）。

### P2-3 上传后自动打标签

**现状**：`saveUploadedFile` 已按扩展名推断四分类（category），kind 亦有推断——链路存在。
**改动点**：满足需求原文「自动为资源打上标签（标记该项目/程序的类型分类）」：
- 压缩包类：kind 细化标记为 `archive`（或 kind=`source` + `label=压缩包`），**原格式存储**（现状即原格式落盘，无解压，保持）。
- 报名场景上传的资源额外打「来源标签」：asset 增加可选字段或 note（如 `signup:<activityId>`），便于个人中心区分「报名作品」与「日常上传」。
- **待确认项 ②**：自动标签的粒度（仅压缩包/源码区分，还是要到 SKILL/程序/文档等业务语义）——首版建议只做机器可判断的粗粒度，业务语义标签交给 P4 的仓库识别。

**涉及文件**：`server/routes/activities.js`（signup/upload 的 createAsset 参数）、`server/lib/asset-store.js`（标签字段）、`public/app.js`（分流 UI）。

**验收**：三种用户路径全部走通——①已有资源用户在报名表内完成选用；②小白直传压缩包看到注释引导且资源带标签入库；③「不会压缩」用户从报名表跳个人中心上传后能回到报名表继续提交（配合 P3 完成闭环）。

## P3 个人中心跳转引导（聚光灯三件套）

**前提**：P2 的跳转入口存在。

### 改动点（`public/app.js` MySection + 新增引导组件）

1. **跳转参数**：个人中心路由支持 `#my?guide=upload`（或 query）标记，进入时自动定位到「我的资源」区。
2. **聚光灯高亮**：引导态下给目标元素（「本地上传」「上传程序」按钮；程序面板内的「复制提示词」按钮）加高亮描边 + 其余区域压暗遮罩（z-index 层叠：遮罩挖洞指向目标），点击目标或「知道了」结束引导。
3. **教程内容**：引导旁挂简短教程卡（3 步内），说明「上传压缩包 → 回报名表 → 选用该资源提交」；「复制提示词」路径的教程说明 agent 操作流程（对齐需求澄清 §4.2 第 3 点「跳转 + 高亮 + 教程三件套」）。
4. 实现约束：纯前端 CSS/JS，`prefers-reduced-motion` 下不做过场动画（项目既定规范）。

**验收**：从报名表点「去我的资源上传」落地即见聚光灯；完成上传后页面提示「已上传，返回报名表」可一键回跳（带活动 id 回到该报名页并自动选中该资源）。

## P4 Github 地址识别（程序面板增强）

**前提**：独立可做，建议 P2 后启动（与 P3 可并行）。

### 改动点

1. **仓库地址双支持**（`public/app.js` 程序面板 + `server/routes/assets.js`）：
   - 输入框实时识别：`gitlab` 域 → 现有流程（默认，走飞书资源中心 agent 链路）；`github.com` → 切换 Github 模式。
   - Github 模式下表单简化：隐藏「资源中心地址/审核状态」等 gitlab 专属字段，显示「识别 README → 提供下载」。
2. **README 识别与下载**：
   - 方案 A（推荐，首版）：服务端新增只读代理接口 `GET /api/assets/github-readme?url=<repo>`，服务端抓取 `raw.githubusercontent.com/<owner>/<repo>/HEAD/README.md`（带 timeout + 域名白名单校验，仅允许 github.com 仓库页解析出的路径），返回内容与下载链接。前端展示 README 预览 + 「下载 README」按钮。
   - 方案 B：纯前端拼 raw 链接直下——不占服务端，但内网用户直连 github 可能失败且无超时控制。
   - **待确认项 ③**：服务器侧是否允许出网访问 github（内网部署约束，PLAN.md D1 决策为内网部署——若服务器无公网出口，方案 A 不可行，需降级为前端直链 + 明示「需自行保证可访问」）。
3. assets 表：Github 登记复用 `repo_url` 字段（POST /api/assets 现有字段足够），`kind` 标 `github-source` 以区分 gitlab 资源。

**验收**：面板输入 github.com 地址即切换模式；能获取该仓库 README 内容并提供下载；gitlab 原流程零回归。
