## 一、核心设计原则（贯穿全部需求）

1. **目标用户 = 零 AI 经验的小白**。用户可能会 SQL、会开发，但只要没接触过 AI/本平台，就不会操作。所有界面布局、文案、操作路径必须简洁明了、直白易懂。
2. **「作品」与「资源」两个概念要打通**：作品是用来发布/报名的，资源是用户自己上传的。报名表和个人中心「我的资源」是同一条链路的两个入口，不是两套孤立功能。

## 二、报名表（活动报名页）改造

### 2.1 布局重做

- 现状「太简陋」，用户完全看不懂字段含义（录屏原话）。
- **必须修复**：表单当前直接暴露 `field_a`、`field_b`（下拉「请选择」）、`field_c` 原始字段名（见关键帧 1，约 0:00 / 2:00 / 3:20 处反复出现）——动态表单的标签未渲染或测试字段残留，小白用户完全无法理解。

### 2.2 字段规则

| 字段 | 规则 |
| --- | --- |
| 姓名 | 登录后**自动读取**，不可修改（现状已预填，保持） |
| 部门 | 登录后**自动读取**，不可修改（现状是空白手填——需接通账号部门数据） |
| 备用联系方式（选填） | 旁边先标出账号绑定的手机号（自动读取），或预留一个窗口填写备用邮箱/手机 |
| 作品文件（必传） | 走上传控件，规则见第三节 |

### 2.3 自动草稿

- 报名表**全程自动保存草稿**；用户中途退出后再进入，必须能继续上一次的编辑内容，不能丢（原话：「不能上传叫什么，不能退出以后就没了」）。

## 三、作品文件上传链路（报名表 ↔ 我的资源）

### 3.1 两种入口情况

- 用户**已在个人中心上传过资源** → 报名表中可直接选用已有资源，不需要重复上传。
- 用户**未上传过** → 从报名表现场上传，按文件类型分流。

### 3.2 按类型分流的上传规则

| 类型 | 处理 |
| --- | --- |
| 普通文件（视频/图片/文档等常规文件） | 保留现有上传入口（单文件 ≤50MB 不变） |
| SKILL / 程序 / 文件夹类 | 引导上传**压缩包**；上传入口旁必须有文字注释：「上传程序类、SKILL 类请先进行压缩，上传压缩包即可」 |
| 不会压缩 / 没有压缩包的用户 | 报名表内放**跳转链接** → 跳转到个人中心「我的资源」完成上传，之后回来继续完成报名提交。原话强调：「他连压缩都不会，我们要考虑这种情况存在」 |

### 3.3 上传后的后台处理

- 上传完成后，后台**自动为资源打上标签**（标记该项目/程序的类型分类）。
- 压缩包类资源直接**以压缩包原格式**存入「我的资源」。

## 四、个人中心「我的资源」引导交互

### 4.1 跳转落地页的动态引导

- 从报名表跳转到个人中心后，页面布局要**动态变化**做新手引导：
  - **高亮**目标操作区域（「本地上传」「上传程序」按钮）；
  - **压暗**非点击区域（聚光灯效果），让用户一眼知道该点哪里。

### 4.2 「上传/登记程序」表单增强（见关键帧 4，约 4:40 处）

现有字段：程序名称、仓库地址（内网 Gitlab）、资源中心地址（agent 回填，用户不填）、「复制提示词」按钮、资源中心审核状态（待处理）、粘贴 agent 报告（留存）。增强点：

1. **仓库地址双支持**：
   - **Gitlab**（默认，走飞书资源中心）；
   - **新增 Github 地址识别**——用户自己的仓库，同样识别 README 等内容，并据此提供下载。
2. **「复制提示词」按钮同样做高亮引导 + 压暗周边**：用户连仓库地址都不会填，就靠提示词去完成 agent 端操作。
3. **配套教程**：引导用户完成 agent 端操作的教程内容要成体系（跳转 + 高亮 + 教程三件套）。
