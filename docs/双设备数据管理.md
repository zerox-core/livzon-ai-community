# 双设备数据管理（快照同步模式）

> 适用于当前阶段：**同一个人、两台电脑分开开发，代码与数据统一走 GitHub 仓库同步**（测试开发阶段，库内为测试数据）。
> 代码用 git，表结构用 `run_migrate.js`，**业务数据用本方案的快照**。不采用跨网共库。

## 一、模型：三样东西三条通道

| 内容 | 通道 | 说明 |
|---|---|---|
| 代码 / 表结构迁移 | git + `node server/sql/run_migrate.js` | 迁移幂等，pull 后跑一次即最新 |
| 业务数据（用户/帖子/报名/资源记录等） | **`sync/db-*.sql` 快照随 git 走** | `pg-keeper dump` 生成、`restore` 还原 |
| 上传文件（`public/uploads/`） | 随快照：`sync/uploads/`（dump 时 `--uploads`） | 目录整体镜像，pull 后 `restore --uploads` 还原 |

每台设备各自的本地库照常存在；快照是**权威数据副本**，"最后一次 dump 即最新状态"。

## 一之二、静态资源（showcase 插图等）走 git，不占快照

`public/showcase/**` 下的插图/网页是**普通 git 跟踪文件**，`git pull` 即得，无需 dump/restore：

| 资源 | 通道 |
|---|---|
| `public/showcase/<slug>/img/illu-NN.jpg`（生成的插图，38 张） | git（随代码） |
| `public/showcase/**/index.html`、`vendor/`（本地化 SDK） | git（随代码） |
| `public/uploads/**`（运行期上传文件，gitignore） | 镜像副本在 `sync/uploads/**`（git 跟踪）；`restore --uploads` 会拷回 `public/uploads/` |
| `server/.env`（凭证/回调地址/DB 密码） | **各设备自备，不入库**（见第四节清单） |

**另一台设备同步这批资源的完整做法**（仓库根目录）：

```bash
git pull --rebase                  # 代码 + 插图 + sync/ 快照与上传文件副本
cd server && npm install           # 仅在 node_modules 缺失时
cd .. && node pg-keeper.mjs doctor # 体检：PG 探测 / .env / 连通性
node server/sql/run_migrate.js     # 表结构对齐（幂等）
# 需要"业务数据 + 上传文件"也与我一致时（会覆盖本地库）：
node pg-keeper.mjs restore --uploads
node start.mjs
```

**不想覆盖本地数据时**：跳过 `restore`，只跑 `pull + npm install + run_migrate`；插图仍会更新（静态文件），上传文件用本地已有的那份。
**验证资源是否齐全**（在任一设备跑，三步）：

```bash
find public/showcase -name 'illu-*.jpg' | wc -l            # 应为 38
grep -rl "/spark/" public/showcase | wc -l                 # 应为 0
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8787/showcase/paper-kite-museum/img/illu-01.jpg  # 200
```

> 体积提示：插图约 27MB，`git pull` 首次会略慢；如需瘦身，在装了 ffmpeg/sharp 的设备上批量降采样即可（当前未压缩）。

## 二、三个命令（pg-keeper.mjs）

```bash
node pg-keeper.mjs doctor          # 体检：PG 探测/.env/连通性/回调地址核对（只读）
node pg-keeper.mjs dump --uploads  # 打快照：sync/db-<时间戳>.sql + sync/uploads/（保留最近 5 份）
node pg-keeper.mjs restore --uploads  # 还原：默认取 sync/latest.json 指向的最新快照
```

- **PG 安装路径全自动探测**：环境变量 `PG_HOME` → `E:\PostgreSQL`（便携机约定）→ `C:\Program Files\PostgreSQL\*`，两台设备都不用手工配环境变量。
- dump 用 `pg_dump --clean --if-exists`，restore 可在空库和已有数据的库上**重复执行**。
- restore 会 DROP 重建各表：**本地未进快照的新写入会被覆盖，会话清空需重新登录**；restore 后建议补跑一次 `run_migrate.js`（快照可能落后于远端最新表结构）。

## 三、换设备标准流程（SOP）

**离开 A 设备前：**
```bash
node pg-keeper.mjs dump --uploads
git add -A && git commit -m "chore(sync): 数据快照 <说明>" && git push
```

**到 B 设备后：**
```bash
git pull
node pg-keeper.mjs doctor     # 看体检是否全绿（首次使用需先在 server/ npm install）
node pg-keeper.mjs restore --uploads
node server/sql/run_migrate.js
node start.mjs                # 启动服务（.env 缺失时会从 env.example 生成，需补飞书凭证）
```

## 四、换设备检查清单

`.env`（每台一份，**不入库**）里这些项与"哪台机器当对外服务主机"有关：

- [ ] `LARK_LOGIN_REDIRECT_URI`：必须指向**运行服务那台**机器的地址。127.0.0.1 仅本机自用；跨设备登录用局域网 IP（如 `http://192.168.62.53:8787/api/auth/callback`）。
- [ ] 飞书开放平台「安全设置 → 重定向 URL」白名单：与上一条**完全一致**（含路径），换主机就加/改一条。
- [ ] `SITE_INTRANET_URL`：飞书卡片按钮指向的服务地址，同上。
- [ ] `DB_*`：各自本地库不用改；仅共库模式才改 `DB_HOST`。
- [ ] `PG_HOME`/`PGDATA`：**已免配置**（自动探测），环境变量有旧值时以它为最高优先，注意别留错值。
- [ ] 跑 `node pg-keeper.mjs doctor`：会逐项核对以上内容并提示不一致（含回调 IP 与本机当前 IP 不符的警告）。

## 五、边界与注意

1. **同一时间只在一台设备上改数据**：快照是"最后写赢"，两台同时各写各的再互相 dump/restore 会互相覆盖。
2. **快照会进 git**（含用户数据/飞书 open_id）：当前为测试阶段且仓库私有，已获确认接受；转入生产或仓库公开前，把 `sync/` 加入 `.gitignore` 并改用私有渠道传快照，同时清理库内测试数据。
3. sync/ 只保留最近 5 份 db 快照（dump 自动清理），uploads 目录整体镜像。
4. `logs/`、`server/.env`、`public/uploads/` 仍按原样不入库；上传文件以快照里的 `sync/uploads/` 为准。
5. 若未来需要**跨网实时共库**（两台同时在线共用一份数据），再上 Tailscale/ZeroTier 虚拟组网或托管数据库，届时 `.env` 的 `DB_HOST` 指过去即可——但注意上传文件仍是单机盘，需另行解决。
